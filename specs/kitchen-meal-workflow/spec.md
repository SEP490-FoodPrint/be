# Kitchen meal workflow: cook one dish at a time

## Context

The kitchen progress screen lists today's dishes with a "Nấu" (cook) action per dish. The system plans batches from stock automatically; the kitchen staff no longer reviews a separate plan dialog. Previously `POST /cooking-batches` and `GET /cooking-batches/plan` accepted `dishId` but always planned the whole meal, so cooking one dish moved every dish of the meal to "Đang nấu".

## Requirements

- **FR-001**: When `dishId` is provided to `GET /cooking-batches/plan` or `POST /cooking-batches`, the plan covers only that dish of the meal (remaining unplanned portions of that dish). Without `dishId`, behavior is unchanged (whole meal).
- **FR-002**: All existing guards still apply to the whole meal before planning: approved menu, active dishes, finalized class portions, positive demand, consistent cooking mode, existing plans not exceeding demand, allergy safety and stock availability.
- **FR-003**: `planVersion` is computed from the dish-scoped plan, so a preview requested with `dishId` matches the create request with the same `dishId`.
- **FR-004**: `batchNumber` is numbered per dish within the meal, starting at 1 and continuing after that dish's existing batches (e.g. a dish with existing Lô 1 gets Lô 2 next). Multi-dish legacy children keep a separate counter.
- **FR-005**: Meal seasonings stay reserved once per meal; consumption still happens only when every dish with demand has fully planned portions and all its batches are completed.
- **FR-006**: No schema or migration change; response envelopes are unchanged.
- **FR-007**: Each cooking batch lot (`cookingBatchLots[]` in list/detail responses) exposes read-only `supplierName`: the name of the supplier of the lot's ingredient (via its delivery item), or `null` when unknown. Batch detail shows the supplier column and the source lot code under the ingredient name.
- **FR-008**: Recording a retained food sample (`POST /cooking-batches/:id/food-samples` and its `/v1` aliases) rejects quantities below the QĐ 1246/QĐ-BYT minimum: 100 for unit `g` (solid food) and 150 for unit `ml` (liquid food), with HTTP 400 on field `quantity`. The minimum is fixed, not configurable per school. Stored historical samples are not changed.
- **FR-009**: Creating or editing a weekly menu (`POST /menus`, `POST /menus/grade-batch`, `PUT /menus/:menuId`, `POST /menus/:menuId/revise-and-submit`) rejects any submitted day that falls on a holiday configured in the school academic year, with HTTP 422 listing the dates and reasons. Holidays added after a menu already exists are not reconciled automatically; existing menu days are not changed.
- **FR-010**: A homeroom teacher's daily meal portion draft (`POST /meal-portions`, `/v1/daily-meal-portions`) is rejected with HTTP 422 when `totalPortions` exceeds the class `registeredMealPortions`. To serve more students the school updates the class registered portions first. This replaces the earlier test that allowed ad-hoc portions above the registered count.
- **FR-011**: Saving and finalizing a daily meal portion are allowed only for today in Vietnam time (UTC+7), on a weekday inside a configured academic year, not on a configured holiday, and only when a menu day for that meal exists for the class (school-wide or its grade). Otherwise HTTP 422 with the reason. Re-finalizing an already finalized record stays idempotent. Records inserted directly in the database are not affected.
- **FR-012**: When creating or editing a weekly menu, every submitted day must lie inside a configured academic year (HTTP 422 otherwise). A day before today (Vietnam time) may only be resent unchanged: adding a new past day or changing its dishes (per meal) returns HTTP 422. Today and later days are unaffected, so the current week stays editable from today on. The menu service accepts an injectable `today` for tests.
- **FR-013**: Weekly menu deadline: a week's menu must be created and submitted for approval by the end of the Sunday before that week (Vietnam date). From that Monday on, creating, editing and submitting the week returns HTTP 422 ("Đã quá hạn lập và gửi duyệt thực đơn tuần …") unless the management board has recorded a `REVISION_REQUESTED` review for that menu, in which case the nutrition officer may still edit (today and later days, per FR-012) and resubmit. The frontend menu list shows a reminder banner when next week's menu is not created or not yet submitted, with the remaining days, per grade (grades without a menu, and menus not yet submitted). `GET /menus/week-schedule` additionally returns `deadline`, `editLocked` and `editLockReason`, and the create-menu screen becomes read-only with that reason when `editLocked` is true.
- **FR-014**: Delivery receipt checks run early. The same read-only checks as the final approval (receipt data, request lines, and for standalone deliveries an ACTIVE school ingredient entry) are evaluated when the school confirms arrival (`POST /deliveries/:id/arrival`) and on inspection detail; the result is returned as `receiptIssue` (string or null). An `APPROVE` decision is rejected with HTTP 409 and that reason as soon as any department signs, instead of failing only at the fourth signature. `REJECT` stays allowed. The frontend adds a "Xác nhận xe đến" button (with confirmation) for in-transit deliveries, asks to confirm arrival after scanning the QR of an in-transit delivery, shows `receiptIssue` in red and disables the approve option.
- **FR-015**: Creating cooking batches (`POST /cooking-batches`, the "Nấu" action) is allowed only for a menu day equal to today in Vietnam time (UTC+7); otherwise HTTP 422 ("Chưa tới ngày …" or "Ngày … đã qua": "chỉ được nấu bữa ăn của hôm nay"). The plan preview (`GET /cooking-batches/plan`) stays allowed for any day because it does not write. Already created batches cannot be undone (unchanged decision); the kitchen screens only load today. `createKitchenService`/`createKitchenLifecycle` accept an injectable `today` for tests.
- **FR-016**: Recording a retained food sample requires `storageUnitId`, a sample storage unit of the school (404 otherwise). The unit must be `ACTIVE` (409 "đang bảo trì" / "đã ngưng sử dụng") and have room: occupancy is `max(currentUsage, STORED samples in the unit)`, the same figure the storage screen shows, and must be below `capacity` (409 "đã đầy"). The unit row is locked `FOR UPDATE` so concurrent samples cannot overfill it. `storageLocation` becomes an optional compartment note; the stored text is "<unit name> – <note>" or the unit name. Responses add `storageUnitId` and `storageUnitName`. An idempotent replay with the same data still succeeds even if the unit is now full. The frontend sample forms select the unit from the school list (full, maintenance and inactive units shown but disabled).
- **FR-017**: Receipt expiry check by handling type (Vietnam date of receipt): `DIRECT_USE` (fresh, used the same day) lots must not be expired (`expiry >= today`); `DRY_STOCK` lots must still be valid for at least 7 days (`expiry >= today + 7`, `DRY_STOCK_MIN_SHELF_DAYS`). The handling type comes from the delivery item's school ingredient entry (or the request line's entry). Messages name the lot and dates, e.g. "Lô … (đồ khô) chỉ còn hạn đến 19/11/2026; cần còn hạn ít nhất 7 ngày kể từ ngày nhận (đến 20/11/2026)". The check is part of `receiptIssue` (FR-014), so it blocks the first APPROVE. Lots without an expiry date are not checked (supplier delivery form to capture dates is a separate change).
- **FR-018**: `GET /supply-requests` accepts an optional `include=items` for school principals. With it, each list item also returns `requestedDeliveryDate`, `sentAt`, `note`, `supplierName`, `supplierPhone` and `items` (`id`, `ingredientEntryId`, `ingredientName`, `handlingType`, `requestedQuantity`, `unit`, `note`), read in the same list query. These are the fields the school already receives from `GET /supply-requests/:id`; without `include` the list projection is unchanged. Any other `include` value returns 400. The school tracking screen reads every page (100 per page, at most 50 pages) of `/deliveries` and `/supply-requests?include=items` instead of the first 100 rows plus one detail call per request, and no longer invents delivery numbers, specs, phone numbers, vehicle plates, temperatures or locations. The default delivery times by order type (dry 14:30, round 2 07:45, round 1 05:30) are kept when the request note has no time.
- **FR-019**: Supplier delivery creation (`POST /deliveries/management`, both `REQUEST` sources and `STANDALONE` items) accepts optional `manufactureDate` and `expiryDate` (YYYY-MM-DD) per line; each line creates one ingredient lot, so the dates belong to that lot. Lines whose school ingredient entry is `DRY_STOCK` require both dates (HTTP 422 naming the ingredients); `DIRECT_USE` (fresh) lines need none. `manufactureDate` must not be after today (Vietnam date) and `expiryDate` must not be before `manufactureDate` (HTTP 400). The dates are stored on the lot and checked again at receipt (FR-017). The idempotency fingerprint includes the dates only when present, so earlier requests without dates keep their fingerprint. `GET /supply-requests/:id` for the supplier returns `handlingType` per line so the form shows the date fields for dry goods.
- **FR-020**: `GET /ingredient-lots` returns `status: "EXPIRED"` for a lot stored as `AVAILABLE` whose `expiryDate` is before today (Vietnam date); the stored status is not changed. The school warehouse screen therefore excludes such lots from available stock and labels lots as Hết hạn / Sắp hết hạn (≤ 3 days) / Khả dụng / Đã dùng hết / Chờ kiểm tra / Đã hủy.
- **FR-021**: System-generated identifiers follow `FP-<2-letter feature>-<sequence>` (at least 5 digits, system-wide numbering per type): ingredient lots created with a delivery `FP-LO-00001` (was `PLAN-01` for every lot), cooking batches `FP-CB-00001` (was `CB-<uuid>`), cooking batch groups `FP-BG-00001` (was `B-<uuid>`), and sample storage units created without a code `FP-SU-00001` (was `TU-LM-01`; a code typed by the user is still accepted and checked for duplicates). Numbers are reserved inside the creating transaction under a PostgreSQL advisory lock per type and continue from the highest existing `FP-XX-<digits>` code; older codes are left unchanged and do not affect numbering. Supply request numbers are not changed.
- **FR-022**: Deliveries that only an ingredient-management signature is needed for: a delivery whose every line is `DRY_STOCK`, or any delivery from the school's dry-goods supplier (a supplier with more `DRY_STOCK` than `DIRECT_USE` active ingredient entries in that school's catalogue). Such a delivery is received after one `INGREDIENT_MANAGEMENT_DEPARTMENT` approval and is hidden from the other three inspection roles (list, counts, scan lookup, detail, arrival and decision answer 404). Other deliveries still need all four roles. The inspection date filter matches a delivery on its expected arrival day and on its actual arrival day.
- **FR-023**: Class allergies are matched to menu ingredients by name, not by exact id: names are NFC-normalised, lower-cased and stripped of punctuation (accents kept), and one name must contain the other on word boundaries ("Đậu xanh" matches "Đậu xanh hạt"; "Đậu" does not match "Dầu ăn"). Only allergies declared with ingredients of suppliers actively linked to the school count. A separate portion group covers an allergy when it avoids the declared ingredient or an ingredient whose name matches it; kitchen demand checks and the homeroom portion-group save use the same rule, and only allergies covered by a group of that meal are reconciled.
- **FR-024**: A round-2 supply request (request number ending `-D2` or `-D2-<n>`) can be created only when every active class with registered meal portions has a `FINALIZED` lunch portion for the delivery date; otherwise 409 lists the classes. The order screen keeps the round-2 button disabled until then.
- **FR-025**: When a homeroom teacher finalises a class meal portion and the meal's menu day is approved with portion groups, the portions are split automatically: the allergy portions declared at attendance go to the first separate group avoiding that allergy, the rest to the default group (422 if declared allergy portions exceed the total). Menu seasoning validation names the ingredients that are not active dry stock.
- **FR-026**: `GET /v1/kitchen` and `/v1/kitchen/stats` keep their school-scoped `RepeatableRead` snapshots and response contracts. Give their read-only interactive transactions a 20-second timeout so a valid large daily kitchen query is not closed by Prisma's shorter default transaction deadline. The database statement timeout remains the existing 15 seconds; this change does not add writes or broaden tenant access.
- **FR-028**: When kitchen planning in `COMBINE_LOTS` mode runs short of an ingredient, HTTP 409 names that ingredient and the remaining shortage in the recipe unit. The eligible-stock and reservation rules do not change; the message uses the menu-day ingredient's existing name and remains generic for callers that do not supply a name. No schema change.
- **FR-029**: A new retained sample must select one of its storage unit's declared compartments (`Ngăn 1` through `Ngăn <compartmentCount>`). The request rejects a missing or custom compartment with HTTP 400/422, and rejects a compartment already held by another `STORED` sample in that unit with HTTP 409, even if the unit was renamed. `DISPOSED` samples release the compartment. Check occupancy inside the existing storage-unit row lock; idempotent replays still succeed. Both sample forms show occupied compartments as unavailable and remove free-text/custom position input. No schema change.
- **FR-030**: Class allergies are declared as numbered groups. Each group is a set of school ingredient entries that one group of students must avoid together, plus that group's student count (for example A: 1, B: 1, A+B: 1 = 3 allergic students). `PUT` class allergies accepts `{ groups: [{ ingredientEntryIds, affectedCount }] }` (the legacy single-list body is one group); the sum of group counts may not exceed the class registered portions, and two groups may not have the same ingredient set. The homeroom daily report sends one `{ groupNo, portionCount }` per class group (0 when the group is absent), each at most the group's count and together at most `totalPortions`. Daily rows snapshot the group composition and reference `ingredient_entries` directly, so editing groups never rewrites or blocks past days. Splitting into portion groups counts each allergy group once, into the special portion group that avoids most of its relevant allergens (ties: fewest avoidances, then order); allocation subtracts each group once from a dish that contains any of its allergens. Migration `20261128000100_class_allergy_groups` adds `group_no` (existing rows become group 1).

## Acceptance

1. A meal with dishes A and B: cooking A creates batches only for A; B remains plannable.
2. Cooking B afterwards creates B's batches with `batchNumber` starting at 1.
3. Calling the endpoint again for a fully planned dish returns `created: false` without new batches.
4. Seasoning consumption is not posted until both A and B batches are completed.
5. Recording a sample of 99.999 g or 149 ml returns 400 on `quantity`; 100 g and 150 ml are accepted.
6. Saving a menu with 20/11 configured as a holiday returns 422 naming 20/11; a week without holiday days saves normally.
7. A class registered for 30 portions: saving 31 returns 422, saving 30 succeeds.
8. Saving or finalizing for yesterday, tomorrow, a holiday, a date outside the academic year or a day without that meal in the menu returns 422.
9. On 18/11, resending Monday 16/11 unchanged with a new Thursday succeeds; adding 17/11, changing 16/11's dishes, or a day after the academic year end returns 422.
10. The week of 23/11 can be created and submitted until 22/11; on 23/11 it returns 422 unless the board requested a revision.
11. A delivery whose data cannot be received reports `receiptIssue` on arrival; the first `APPROVE` returns 409 with that reason and records no decision.
12. Cooking the 11/11 menu on 10/11 or 12/11 returns 422 without creating groups, batches or reservations; the preview still works.
13. Recording a sample into a unit under maintenance or at capacity returns 409 and stores nothing; into an active unit with room it stores `storageUnitId` and "Tủ 1 – Ngăn 2".
    13a. A second active sample cannot use the same unit and compartment; an out-of-range/custom/missing compartment fails; after disposal the compartment can be reused. The forms only offer declared free compartments.
14. A new delivery's lots, a new meal plan's group and batches, and a storage unit created without a code receive `FP-LO-`, `FP-BG-`, `FP-CB-` and `FP-SU-` codes continuing from the highest existing number.
15. Received on 13/11: a dry lot expiring 19/11 is rejected at the first APPROVE, 20/11 is accepted; a fresh lot expiring 12/11 is rejected, 13/11 is accepted.
16. `GET /supply-requests?include=items&limit=100` as a school returns the request lines in the list response with one database query; `include=all` returns 400.
17. Creating a delivery for a dry-goods request line without dates returns 422 and creates nothing; with dates the lot stores them; a fresh line needs no dates.
18. On 18/11 an `AVAILABLE` lot expiring 17/11 is listed as `EXPIRED`, one expiring 18/11 stays `AVAILABLE`; `DEPLETED`/`BLOCKED` lots keep their status.
19. A dry-goods-only delivery, or a delivery from the dry-goods supplier, is received after one ingredient-management approval; the kitchen role gets 404 for it; a fresh delivery from another supplier still needs four approvals.
20. Class allergy "Đậu xanh" flags menu ingredient "Đậu xanh hạt"; a separate group avoiding "Tôm nõn tươi" covers allergy "Tôm nõn".
21. Creating a `-D2` request while a class has no finalized lunch for that date returns 409 naming the class.
22. Finalising 30 portions with 1 declared "Đậu xanh" allergy portion, on an approved meal with a group avoiding "Đậu xanh hạt", stores 29 default + 1 separate.
