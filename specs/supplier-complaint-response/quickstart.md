Tính năng này chuẩn bị shared storage (`complaintCode` + sequence), pure formatter/parser và allocator nội bộ theo [contracts/complaint-code-producer.md](contracts/complaint-code-producer.md), đồng thời triển khai luồng xem/chi tiết/phản hồi chính thức phía nhà cung cấp và chi tiết `SCHOOL` theo `FR-011`.

Điều kiện môi trường và dữ liệu kiểm thử:

- Dùng Node theo .nvmrc và npm theo package.json; npm ci nếu dependencies chưa có, prisma:generate khi cần client.
- Dùng tài khoản/session và dữ liệu khiếu nại được phép trên môi trường kiểm thử. Không tạo account/mock data trong database thành viên để chạy thử.

- Schema hiện chưa có complaintCode; cần migration mới đã review và authorization cho đúng target khi triển khai. Giai đoạn plan không chạy DDL/deploy, db:push, seed/bootstrap hoặc thao tác Azure. Credentials cấu hình không tự mang ý nghĩa cho phép ghi DB. Không sửa applied history/baseline hoặc reset dữ liệu để nhận cột mã.
- Hai supplier roles đã có default view_details/respond trong catalog. Với role/tài khoản thực tế thiếu quyền, operator dùng quy trình quản trị quyền hiện hành; không tự seed hoặc thay grants. Denial/inactive flags vẫn được giữ.

## 2. Kiểm tra chất lượng và unit

Chạy từ repository root sau triển khai:

```bash
npm run prisma:validate
npm run prisma:generate
npm run validate
npm run test:unit
```

Suite mới tests/ingredient-quality-feedback.test.ts và tests/complaint-code.test.ts phải được đăng ký trong test:unit. Kết quả cần ghi số pass/fail thực tế và nguyên nhân nếu bị chặn; không dự đoán đạt.

Unit/HTTP cần chứng minh:

- Admin/staff có view_details được xem; chỉ view_own403; respond không đi kèm view_details403; đủ hai quyền mới ghi.
- UUID/query/body strict; defaults1/20, limit100, page quá cuối; nhiều field sai cùng error.fields tiếng Việt.
- Text Unicode/trim/newline, boundary1/5.000/5.001, blank/null/non-string, field giả mạo actor/status/time bị400.
- Supplier list safe fields và ISO/null; school code null không fallback UUID; detail users chỉ id/fullName.
- complaintCode string bắt buộc đúng mã đã lưu, id/path vẫn UUID; paths bằng FP-CP-code và body phản hồi tự đặt complaintCode bị400. Code thiếu/sai trên endpoint mới503, không null/fallback/cấp số lúc đọc.
- Formatter/parser BigInt: 1/99999/100000/MAX_BIGINT, reject0/âm/vượt range/noncanonical; code sau99999 không cắt số. Supplier list/detail/response không gọi allocator, kể cả callback retry.
- Detail lô null/đúng/khác delivery; thiếu tuple response trả lỗi an toàn; foreign/nonexistent cùng404.
- Conditional write409, retry actor query và direct COMMIT adapter conflict, rollback khi readback lỗi, lỗi thường503 không lộ SQL.
- Legacy SCHOOL/SYSTEM list giữ scope/projection/id ASC; SYSTEM detail và SCHOOL response403.
- POST thiếu CSRF bị403 theo middleware; list/detail/response thiếu session401 trong điều kiện CSRF hợp lệ khi cần.

## 3. Integration trên instance disposable được cho phép

Sau khi authorization và local configuration đáp ứng mục1:

```bash
npm run test:local:check
npm run test:local:migrations
npm run test:local:authorization
```

Nhóm migrations chạy tests/migrations.test.ts trên DB tạm; bổ sung kiểm chứng cột/code/sequence/backfill trong harness hiện có. Nhóm authorization đã được cấu hình chạy tests/authorization.integration.test.ts rồi tests/supplier-onboarding.integration.test.ts bằng hai child tuần tự. CI có các nhóm test tương ứng; không cần runner/workflow mới.

Migration validation cần chứng minh: backfill deterministic theo created_at ASC/id ASC, giữ UUID và mọi cột lịch sử/timestamps; code required/unique/canonical/range; bảng rỗng next1, N rows nextN+1; code từ100000 không bị cắt. Xác nhận không thêm default định dạng code, function/trigger hoặc Counter table, không sửa CHECK response cũ.

Harness tạo fixtures bên trong DB tạm của nó, không thêm seed runtime:

- Supplier A/B; admin và staff mỗi đơn vị; School X/Y cùng gửi cho A, X cũng có chuyến do B giao.
- Khiếu nại SUBMITTED/RESPONDED, lot null, lot đúng, lot cố tình khác chuyến; đủ dữ liệu nhiều trang và createdAt trùng nhau. Fixtures mới lấy số qua shared repository allocator, format rồi INSERT code cùng transaction theo producer contract; không hardcode các mã có thể trùng hoặc cấp code trong supplier handlers.
- School.code null và code trùng; người gửi/người phản hồi đổi membership hoặc bị khóa sau khi tạo lịch sử.
- Relationship ACTIVE/SUSPENDED/UNLINKED, trường inactive, hợp đồng expired; không giả định mọi fixture chỉ có current ACTIVE relationship.

Kết quả cần xác nhận:

1. A chỉ xem/phản hồi khiếu nại chuyến của A dù X cũng liên kết B; foreign ID và nonexistent ID cùng404.
2. Mọi trang khi data đứng yên không mất/trùng item, đúng thứ tự và hasNext.
3. POST của admin/staff hợp lệ200, trường X có view_details đọc được cùng response/id/complaintCode như bản ghi gốc; school view_own chỉ đọc được khiếu nại chính mình gửi. Người X không đọc khiếu nại Y; không giả định BGH đã có default grant đọc.
4. Khiếu nại lịch sử vẫn xử lý được; lô sai không lộ định danh/mã và không để lại response nếu readback phát hiện lỗi.
5. Snapshot nội dung/người gửi, Delivery/Lot/School/Relationship/Contract/User timestamps trước/sau không đổi do chính thao tác response; chỉ complaint được cập nhật. Không so sau một test quản trị đã cố ý đổi user timestamps.
6. Hai phản hồi hợp lệ đồng thời: chính xác một200, một409; giá trị winner giữ nguyên sau repeated POST.
7. Dùng barriers kiểm soát interleaving response với denial/status/role replacement; không dùng sleep để đoán ai lấy lock trước. Admin writer commit trước → callback stale retry và bị403; response nhận lock trước → commit hợp lệ rồi admin writer có hiệu lực cho request kế tiếp. Xác nhận không 503 do sanitize conflict quá sớm.
8. Cùng session cũ nhưng account locked/membership/role/grant/denial thay đổi được áp dụng ở request tiếp theo; không tin claim role/org của token. Permission inactive bị chặn.
9. Giữ tests/modules.test.ts và các regression authorization/supplier-staff/direct adapter retry hiện có.
10. Nhiều producer-contract fixture transactions ở các trường khác nhau cấp mã toàn hệ thống không trùng; rollback không lưu đơn nhưng có thể để gap. Đọc nhiều lần/POST response/retry không đổi code hoặc last_value/is_called của sequence; đối chiếu trong test riêng không có producer cạnh tranh để tránh kết luận sai.

## 4. Smoke flow thủ công

Dùng session cookies kiểm thử hợp lệ trong môi trường được phép, theo contract:

1. Supplier A GET list; chọn feedbackId UUID thuộc A và ghi nhận complaintCode của cùng đơn.
2. Supplier A GET detail; kiểm tra school/delivery/lot và response null.
3. Supplier A POST response với JSON supplierResponse, header X-CSRF-Protection:1 và Origin đúng cấu hình nếu gửi.
4. Supplier A GET detail và trường sở hữu GET detail bằng session riêng; so sánh id UUID/complaintCode/nội dung/người/thời điểm, mã giữ nguyên như danh sách và nguồn tạo đơn.
5. POST lại nhận409; B GET cùng id nhận404; trường không sở hữu nhận404; thiếu quyền403.
6. Ghi kết quả thật, không đưa cookies/password/connection URL hoặc nội dung nhạy cảm vào output/tài liệu.

Không cần thay API bằng Bearer token hoặc thêm cơ chế login mới; giữ cookie/CSRF runtime hiện hành.

## 5. Tài liệu, rollout vận hành, spec gate và nghiệm thu

- **Kiểm kê writer và cửa sổ bảo trì (T043)**: Rà soát toàn bộ repo và dịch vụ ngoài repo (kể cả legacy script/cron nếu có) ghi vào `foodprint.ingredient_quality_feedback`. Trong codebase hiện tại, chưa có writer/HTTP endpoint tạo đơn nào (`ingredientQualityFeedback.create`/`createMany` chỉ mới có trong fixture integration tests). Khi triển khai vận hành có writer tạo đơn bên ngoài, bắt buộc tạm dừng ghi khiếu nại trong cửa sổ bảo trì được duyệt, áp dụng migration `20261120000300_ingredient_feedback_complaint_code`, kiểm tra backfill/sequence rồi mới bật backend/producer đã cấp `complaintCode` (không rolling writer cũ thiếu `complaintCode` do cột là `NOT NULL` không default).
- **Quyền DB sequence theo operator**: Tài khoản DB runtime của producer (khi được owner BGH triển khai) cần quyền `USAGE` trên `foodprint.ingredient_quality_feedback_complaint_code_seq` theo quy trình quản trị DB hiện hành; feature supplier không tự thực thi `GRANT`, `deploy` hay `auth:bootstrap`.
- **Phụ thuộc producer BGH & rollback forward-fix**: Producer HTTP Ban Giám hiệu và default `submit`/`view_details` cho `SCHOOL_MANAGEMENT_BOARD` chưa có trong repository — đây là phụ thuộc tích hợp riêng, không coi fixture integration là nghiệm thu luồng BGH thật. Nếu cần rollback ứng dụng sau migration, **không** chạy lại writer thiếu `complaint_code`, **không** `DROP` cột, **không** reset sequence hay sửa migration đã áp dụng; giữ chế độ tạm dừng ghi và xử lý theo quy trình forward-fix được duyệt.
- Đã đồng bộ `src/modules/README.md`, `docs/AUTHORIZATION.md` và `database/SCHEMA_BASELINE.md` với matrix supplier list/detail/respond, SCHOOL detail `FR-011`, legacy SCHOOL/SYSTEM list, cột `complaint_code`/sequence và trạng thái **chưa triển khai lên DB thành viên hoặc Azure**.
- Kiểm tra Markdown định dạng, liên kết nội bộ và không còn placeholder; đối chiếu FR-001–FR-015 theo bảng coverage trong plan và tasks đã cập nhật.
- Chạy `npm run spec:check` với base/head/ref đúng feature diff khi đã có artifacts plan/tasks và thay đổi được Git xét. Nếu HEAD chưa chứa thay đổi, phải kiểm tra bằng diff/index được script hỗ trợ hoặc báo chưa kiểm chứng; không lấy kết quả no-op làm bằng chứng.
- Không tự commit/push để tạo bằng chứng; ghi rõ task chưa chạy nếu còn prerequisite.
- **SC-001–SC-005** chỉ ghi đạt sau unit/integration tương ứng. **SC-006** đo riêng với giao diện đầy đủ (>= 90% hoàn thành trong 2 phút ở lần đầu): **hiện chưa đo** và không thuộc phạm vi backend này.
