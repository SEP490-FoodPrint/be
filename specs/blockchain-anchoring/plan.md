# Kế hoạch

Mỗi nghiệp vụ có một bảng version riêng, cùng khung cột nhóm A và B (`BLOCKCHAIN_GLOBAL.md` mục 3.1). Version được tạo `PREPARED` trong transaction nghiệp vụ. Sau khi commit, service gửi ngầm giao dịch theo đúng cách của module phân phối suất ăn trên nhánh `feat/blockchain-modules`. Hạ tầng hash và client lấy nguyên văn từ nhánh đó. Hàm dựng payload là hàm thuần nên test không cần hạ tầng.

Không dùng code cũ trong `stash@{0}` (outbox, worker, client tự ký).

## Quy tắc kỹ thuật

- Lấy `ethers` qua `blockchain.ts`; chỉ thêm `ethers.id` để tạo `recordId`.
- `network_name` lấy từ `BLOCKCHAIN_NETWORK`, không dùng `networkName` mà `blockchain.ts` trả về.
- So sánh hash bằng chữ thường.
- Không đổi hành vi nghiệp vụ. Không sửa `traceability_anchors`, module `traceability`, contract hay hai file chép từ `feat/blockchain-modules`.

## Rủi ro đã biết

- `canonicalizeJson` sắp key bằng `localeCompare`, biến `Date` thành `{}` và serialize `Decimal` theo cấu trúc bên trong. Spec này tránh lỗi bằng cách chỉ đưa kiểu nguyên thuỷ vào payload. Cần báo nhóm vì module phân phối suất ăn có thể bị ảnh hưởng. Nếu sau này hàm đổi, hash cũ không tái tạo được, nên giữ `payload_version` và `hash_algorithm` để phân biệt.
- `blockchain.ts` tạo provider mới mỗi lần và không tắt cache nonce. Hàng đợi tuần tự trong tiến trình tránh trùng nonce khi chạy một instance API. Chạy nhiều instance cùng một ví thì vẫn có thể trùng nonce; khi đó version `FAILED` và gửi lại qua API `anchor`.
- Khi tiến trình tắt giữa chừng, version còn `PREPARED`. Không có tự động thử lại; phải gửi lại qua API `anchor`.
- Tiến trình API giữ private key của ví Writer.
- Hai file chép nguyên văn phụ thuộc vào nhánh `feat/blockchain-modules`. Nếu nhánh đó sửa trước khi merge thì phải đồng bộ lại.
